# v0.2 Semantic Correctness

Статус: release-contract на 5 августа 2026 года.

Цель этапа — не расширить число операторов, а гарантировать одно из двух:
поддерживаемая PyTorch-модель сохраняет смысл на всём пути до RTL либо
компиляция останавливается с понятной ошибкой до генерации RTL.

## Граница версии Python

Release-контракт v0.2 поддерживает только Python `>=3.12,<3.13`. Поддержка
Python 3.11 и Python 3.13 не заявляется: frontend зависит от проверенного для
Python 3.12 bytecode/code-object контракта, а частичная адаптация отдельных
opcode или атрибутов не считается поддержкой новой версии Python.

## Поддерживаемое подмножество

Frontend принимает один тензорный вход со статической формой и один тензорный
выход. Контейнер input shape должен быть конечным `Sequence` (не string/bytes,
set или одноразовый iterator), ранг не превышает 64, все размеры — положительные
built-in `int`, а тензор содержит не более 1 000 000 элементов. Вычислительные
FX-узлы обязаны образовывать одну последовательную цепочку: каждый следующий
узел использует результат предыдущего, а настоящий `output` возвращает последний
узел цепочки. Ветвления, skip-connections, несколько входов/выходов, tuple/list/
dict output и произвольный DAG отклоняются через `UnsupportedOpError`.

Поддержаны только следующие FX-формы:

- `call_module` для `nn.Conv2d`, `nn.ReLU`, `nn.Flatten`, `nn.Linear`;
- `torch.argmax(...)` и `Tensor.argmax(...)` как финальная операция.

Ограничения операторов:

- `Conv2d`: вход `(C, H, W)` без batch, `groups=1`, `dilation=1`,
  `padding_mode="zeros"`, статические целочисленные kernel/stride/padding;
- `ReLU`: поэлементно, форма не меняется;
- `Flatten`: только полное превращение тензора в один вектор;
- `Linear`: только вход формы `(in_features,)`, prefix/batch dimensions не
  поддержаны;
- `Argmax`: только глобальный `dim=None, keepdim=False`, только последним узлом;
  `dim=...`, `keepdim=True` и `out=...` отклоняются.

Functional-варианты `linear`, `relu`, `conv2d`, произвольные tensor methods,
динамический control flow и другие FX-узлы в подмножество не входят.

Поддерживаемые leaf-модули должны быть стандартными экземплярами точных типов,
перечисленных выше. Subclass, custom metaclass, instance-level override
`forward`, forward/pre/backward hook и глобальные registration/forward/backward
hook registries отклоняются: их эффекты не представлены в текущем GraphIR. Для
каждого, включая вложенный, модуля проверяются
`__call__`, `_call_impl`, `_wrapped_call_impl`, compiled call path,
`__getattribute__`, `__getattr__`, instance `forward` и module-introspection API.
Обход не доверяет переопределяемым `named_modules`, `named_parameters` и
`named_buffers`, а читает внутренние module registries. Custom copy protocol,
decorated `forward`, class-level state и изменяемое внешнее Python state также
отклоняются до выполнения пользовательского forward.

Custom `forward` и достижимые helper methods проверяются закрытым списком
безопасного bytecode и не могут содержать nested code objects, Python conditional
jumps, loops, exception handling, FX Proxy introspection или tensor-dependent
string formatting. Для v0.2 это честно фиксирует отсутствие динамического Python
control flow и исключает различия между объектом FX Proxy и реальным Tensor во
время исполнения. `co_consts` рекурсивно допускает только точные immutable
примитивы/контейнеры, а function builtins mapping и используемый `len` должны
совпадать со стандартными Python bindings.

Внутренние registries `_parameters`, `_buffers`, `_modules` нельзя читать из
custom `forward`: такой обход возвращает реальные mutable objects мимо FX Proxy.
Прямое tensor/Parameter/ndarray instance-state вне стандартных registries также
не поддержано. Требуемый `weight` у `Linear`/`Conv2d` обязан быть обычным
`nn.Parameter`; `bias` может быть таким же параметром либо `None`.

Frontend фиксирует исходные стандартные классы и используемые bindings PyTorch и
отклоняет их monkeypatching, включая изменение function code, globals,
dtype/layout constants, Tensor metadata/conversion API и functional
`linear`/`conv2d`/`relu`. Параметры и buffers принимаются только с точными
built-in string-именами в registries, на CPU, с layout `strided`, contiguous
storage, без tensor subclasses, conjugate/negative view bits и сохранённого
`.grad`. Проверяются точечные PyTorch-привязки без нестабильного отпечатка всего
динамического класса `Tensor`. Это намеренный board-independent CPU-контракт
v0.2, а не обещание поддержки GPU или autograd.

Трассировка выполняется на проверенной глубокой копии модели; binding/code
`copy.deepcopy` защищён, а структура копии сравнивается по точной идентичности
типов, не по подменяемым строкам `__module__`/`__qualname__`. Frontend сравнивает
module-owned Python/tensor state и определения всех custom module classes до и
после: мутация отклоняется без изменения исходной модели. Любое обычное
исключение `symbolic_trace`, включая dynamic tensor control flow, оборачивается в
`UnsupportedOpError`. После lowering отдельная concrete semantic probe на копии
модели проверяет точные dtype, форму и значения настоящего output против GraphIR
на нулевом и детерминированном ненулевом входах, каждый раз на новой копии и с
повторным контролем мутаций.
`ReLU(inplace=True)` не поддержан: мутация входного тензора не является частью
RTL-контракта. Это намеренное сужение контракта, предотвращающее молчаливую
потерю PyTorch-семантики.

Для `Conv2d` обе компоненты `kernel_size` и `stride` должны быть положительными
целыми числами, а `padding` — неотрицательным. `bool`, дробные значения,
несогласованные формы weight/bias и неположительная выходная форма отклоняются
через `UnsupportedOpError` до quantization.
`kernel_size`, `stride`, `padding` и максимальная положительная координата
индексации должны помещаться в signed 32-bit SystemVerilog `int`; полный output
`Conv2d` ограничен 1 000 000 элементов. Это предотвращает Python ↔ RTL
расхождение из-за переполнения loop/index arithmetic и слишком большой concrete
semantic probe.
`in_channels`, `out_channels`, `groups`, `in_features` и `out_features` должны
быть положительными built-in `int`; zero-sized outputs запрещены. Размерности
input shape и `Flatten.start_dim/end_dim` также требуют точный built-in `int`,
без неявного преобразования строк, `bool` или integer subclasses.

## Floating dtype

Поддержаны однородные модели `torch.float32` и `torch.float64`. Dtype хранится в
`TensorIR`, параметры остаются в исходном NumPy dtype, а float reference выполняет
`Linear`, `Conv2d` и `ReLU` через PyTorch functional kernels в dtype графа. Это
сохраняет не только dtype, но и PyTorch-порядок накопления/FMA около cancellation
и tie. Вход reference приводится к зафиксированному dtype графа. `float16`,
`bfloat16`, complex, integer/bool parameters или buffers и смешанные dtype
отклоняются frontend.

Промежуточные активации сравниваются по одинаковым именам и формам: для
`float32` используются `rtol=1e-5, atol=1e-6`, для `float64` —
`rtol=1e-12, atol=1e-12`; класс сравнивается точно. Cancellation/near-tie
regressions для `Linear` и `Conv2d` гарантируют, что ни повышение `float32` до
`float64`, ни другой порядок NumPy-накопления не меняют класс.

## Семантика выхода

`GraphIR.output` совпадает с настоящим PyTorch `output`. Если модель возвращает
логиты, GraphIR тоже возвращает логиты и не содержит выдуманного `ArgmaxIR`.
RTL-порт `logits` передаёт эти значения, а `class_id` является дополнительным
производным выходом hardware-lowering. Если модель явно заканчивается допустимым
глобальным `argmax`, он присутствует в GraphIR и становится настоящим скалярным
выходом модели с dtype `int64`, как у `torch.argmax`.

Reference API однозначен:

- `result.output` — настоящий semantic output модели;
- `result.logits` — тензор до explicit argmax либо сам output logits-модели;
- `result.class_id` — целочисленный первый глобальный максимум;
- `result.activations[-1]` — именованный результат последней IR-операции.

Для explicit argmax `output` скалярный и равен `class_id`, а `logits` сохраняет
исходную многомерную форму. Для модели без explicit argmax `output` и `logits`
совпадают, а `class_id` является дополнительным hardware/reference-результатом.
Многомерный tensor сохраняет форму в GraphIR/reference, но сериализуется одной
плоской строкой на вектор, потому что RTL-порт является плоской шиной.

## Fixed-point контракт

Для конфигурации `bits=B`, `frac_bits=F`, `acc_bits=A` действует единый безопасный
диапазон Python/files/SystemVerilog/testbench:

```text
2 <= B <= 32
0 <= F < B
B < A <= 64
```

Все три поля должны быть целыми и не `bool`.

Арифметика:

```text
quantize: finite float * 2**F -> np.rint (ties-to-even) -> signed-B saturation
MAC:      (bias_q << F) + sum(input_q * weight_q)
requant:  arithmetic MAC >> F
output:   signed-B saturation
argmax:   первый максимум (строгое сравнение >)
```

NaN и infinity не квантуются. Сырые fixed-point input/weight/bias сначала
проверяются в исходном dtype и только затем приводятся к `np.int64`. `bool`,
object, string, complex, NaN/infinity и дробные значения отклоняются. Signed и
unsigned integer, а также конечные integer-valued float принимаются только если
точно лежат в signed `B`-битном диапазоне. Поэтому `uint64(max)` не может
превратиться в `-1`, а `1.9` — в `1`.

Переполнение аккумулятора не является допустимой семантикой. Перед созданием
RTL компилятор вычисляет интервальную верхнюю оценку для каждого произведения,
сдвинутого bias и каждого промежуточного MAC-prefix с учётом реальных
квантованных весов и полного диапазона входа. Если хотя бы один интервал не
помещается в signed `ACC_BITS`, генерация останавливается с `OverflowError`, где
указаны операция, место, возможный диапазон и минимальная ширина.

## Проверки эквивалентности

- PyTorch float ↔ GraphIR float: финальный результат и активации каждого слоя
  для MLP и `Conv2d -> ReLU -> Flatten -> Linear`;
- GraphIR float ↔ fixed reference: точный тест на представимых значениях плюс
  logit-error в `report.json` для сгенерированных векторов;
- Python fixed-point ↔ RTL: bit-exact все логиты и `class_id`; directed тест
  Linear и Conv2d включает padding, stride, `-128`, `127`, zero, отрицательные
  значения, saturation и tie-case;
- overflow: runtime reference проверяет каждое произведение/сложение, а
  compile-time анализ не позволяет создать RTL с возможным wraparound;
- Yosys: parser поддерживает count-first и строки вида
  `Number of cells: 115`; метрики и типы cells записываются в `report.json`.

Именованные промежуточные значения доступны как `result.activations` у
`infer_float_graph()` и `infer_quantized()`.

`vector_count` обязан быть положительным. Testbench получает точное ожидаемое
число векторов, проверяет и полностью потребляет input/classes/logits без
недостающих, лишних или нечисловых значений. Каждый token обязан быть
канонической signed decimal записью (`str(integer)` без `+`, ведущих нулей и
суффиксов). Metadata фиксирует `data_bits`,
размеры входа/логитов и число классов и сверяется с localparam сгенерированного
testbench. Input/logits обязаны лежать в signed `B`-битном диапазоне, а class —
в диапазоне `[0, class_count)`, поэтому wrap/truncation alias не может дать
ложный успех. Сам testbench сначала читает token как строку, затем требует
канонический результат 64-битного signed разбора и только после этого проверяет
диапазон до среза аппаратной ширины; поэтому значение с добавленным `2^64` не
может обернуться в исходное. Host parser лексически различает SystemVerilog code,
строки с escape-последовательностями, line comments и block comments, поэтому
текст `localparam` внутри строки/комментария не может скрыть реальный контракт;
testbench с preprocessor directives отклоняется. Перед запуском runner заново
рендерит канонический `tb_top.sv` из текущего шаблона и требует полного
byte-for-byte совпадения, поэтому дополнительный ранний `$finish` или второй
`PASS` невозможен. Contract localparams должны идти в фиксированном generated
header непосредственно после `module tb_top`; значения ширин и размеров также
сверяются с `report.json`, `vectors.json` и parameter header `top.sv`. Во всех
компилируемых DUT sources вне канонического testbench запрещены preprocessor и
simulation-control constructs/system tasks, поэтому ранний `$finish` нельзя
перенести в `top.sv` или вспомогательный RTL-модуль.
Кроме того, `report.json` хранит SHA-256 каждого сгенерированного RTL source, и
runner сверяет полный manifest до запуска EDA. Перед `synth` отдельный preflight
также связывает quant widths, vector metadata, input/logits sizes в report с
header `top.sv`/testbench, не требуя пригодности самих vector payload files.
Поэтому одиночное изменение `defparam`, иерархическая ссылка на checker, ложная
ширина в report или другая правка compile artifacts не проходит как исходный
compile output.

Граница этой проверки намеренно уже полноценной защиты от злонамеренной
подмены. Канонический testbench и SHA-256 manifest гарантированно связывают RTL
sources, а structural/range/bit-exact проверки vectors и обязательной report
metadata обнаруживают случайное или несогласованное повреждение проверяемого
контракта. Поэтому одиночное несогласованное изменение RTL, testbench, vector или
contract-bearing report metadata даёт failure до EDA либо в bit-exact
симуляции. Это не гарантирует обнаружение произвольной замены допустимого vector
payload, которая не меняет результат модели, или несвязанного report-поля вроде
`reference`. Manifest хранится в том же build directory и не является внешним
корнем доверия. Согласованная модификация RTL, vectors, report и локальных хешей
одновременно находится вне модели защиты. Для такого сценария потребовалась бы
внешняя подпись, доверенный manifest либо полная регенерация build directory из
доверенных исходников.

`PASS vectors=N` принимается runner только при `N > 0` и совпадении
с `vectors.json` и testbench. При invalid vectors JSON/HTML-визуализация сразу
получает тот же failure status и не сохраняет старый `PASS`.
Повреждённый `report.json` также переводит API и CLI в failure до EDA; failure
status записывается контролируемо, а прежний `PASS` удаляется из report и
визуализации. Build после такого preflight остаётся недействительным до полной
регенерации.

Успешный Yosys synthesis/stat не зависит от пригодности verification-векторов
для подробного visualization trace: при повреждённом trace synthesis result и
метрики сохраняются, а визуализация безопасно переходит в status-only режим.
Даже структурно повреждённый `visualization.json` не отменяет уже успешный
Yosys result: authoritative status остаётся в `report.json`.

Явные CLI-команды `verify` и `synth` возвращают ненулевой код при отсутствии
соответствующего инструмента. В объединённом demo-flow эти EDA-этапы остаются
явно помеченными optional/skipped.

`examples/tiny_mlp/compile.py` требует `--checkpoint` и загружает именно этот
checkpoint; путь train → checkpoint → compile покрыт regression-тестом.
В wheel включены runtime model-файлы четырёх встроенных demo, поэтому
установленная команда `torch2rtl demo` не зависит от исходного checkout.

## Критерии готовности

- поддерживаемое подмножество определено этим документом и regression-тестами;
- неподдерживаемая семантика отклоняется frontend до RTL;
- PyTorch и float GraphIR совпадают на тестовых моделях по слоям;
- Python fixed-point и Icarus RTL совпадают на обычных и граничных векторах;
- недостаточный `ACC_BITS` обнаруживается до записи `top.sv`;
- пустые или повреждённые vector-файлы не могут дать успешный статус;
- Yosys-метрики попадают в `report.json`;
- полный `pytest` и board-independent `tiny-conv` demo проходят.

Проверка accuracy обученной CNN относится к следующему этапу и не является
частью Semantic Correctness.
